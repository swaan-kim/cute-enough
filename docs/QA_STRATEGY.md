# 옆집 강아지 전체 QA 기준

2026-09-13 · **정상 앱의 사용자 여정 + 서버 불변 조건 + Toss 실기기 확인**을 분리한다. [최근 점검·회귀 결과](THIRD_INTERACTION_PHOTO_20260913.md)

자동 테스트가 통과해도 운영 DB 적용·Edge 배포·AIT 업로드·실기기 검증·출시가 완료된 것은 아니다. 기존 사용자 기록을 지우거나 별도 진단 화면으로 이동해야만 가능한 테스트를 기본 QA로 삼지 않는다.

## 1. 실행 방법과 확인 수준

```powershell
npm ci
npx playwright install chromium
npm run test:flows
```

| 명령 | 실제로 확인하는 범위 | 대신하지 못하는 것 |
| --- | --- | --- |
| `npm run test:server` | 격리 PGlite의 실제 SQL/RPC, 실제 Edge 처리기와 가짜 외부 응답, 로컬 검수 서버·AIT 보관 검증 | 운영 PostgREST/Storage/mTLS, 실제 다중 DB 연결 경쟁 |
| `npm run test:regression` | 앱·검수 UI·SDK 연결 코드·알림 worker·정책·타입 검사 | 실제 네이티브 SDK와 광고 재고 |
| `npm run test:e2e` | 실제 App·TDS·SVG·API 클라이언트·광고 컨트롤러를 Chromium에서 조작 | 서버는 로컬 HTTP fixture, SDK는 네이티브 경계 대역 |
| `npm run test:e2e:dev` | 실제 개발 React StrictMode 첫 진입·재조회 | 운영 배포 상태 |
| Toss QR 수동 확인 | 실제 AIT + 실제 백엔드 + 테스트 사용자 A/B + 네이티브 SDK | 이 결과도 일반 사용자 출시 완료와는 별도 |

브라우저 테스트는 360×640, 390×844, 430×844에서 실행한다. 각 테스트는 독립적인 브라우저 저장소와 사용자 상태로 시작하므로 운영자의 이미 모은 사진 때문에 티켓이 줄지 않는 문제 없이 `2→1→0`을 반복 검증한다. 실제 계정의 앨범·티켓은 초기화하지 않는다.

자동 실행은 운영 환경 파일을 불러오지 않는다. Edge 네트워크는 거부하고, 브라우저의 예상하지 못한 외부 요청은 실패시킨다. 패키지·브라우저 설치는 최초 준비 단계에만 네트워크가 필요하다. 사진과 SVG는 테스트 전용 자료를 쓴다. [브라우저 테스트 경계](../tests/e2e/README.md).

## 2. 핵심 시나리오와 통과 기준

| 여정 | 반드시 확인할 결과 | 주된 자동 증거 |
| --- | --- | --- |
| A가 이름과 사진 1~5장 등록 | 한 강아지로 저장, 빈 이름·6장·실패 파일 차단, 같은 요청 재시도 시 중복 등록/보상 없음 | 등록 UI·API·SQL 테스트 |
| 검수 전 A/B 차이 | A는 내 사진 접근, B는 캐릭터만; B 응답에 원본 경로·실사 URL·편집 상태 없음 | API/Edge 권한 테스트, 다중 사용자 SQL |
| 검수 초안→명시 확정 | 초안은 미공개, 확정 SVG의 정규화 SHA·버전 보존, 구형/충돌 승인 거부 | 검수 HTTP·SVG SQL·렌더러 테스트 |
| 승인 후 A/B | A는 최종 외형, B는 같은 공유 링크의 승인 상태; 오늘 집은 고정하고 후보 편입은 다음 KST 날짜 | 캐시·공유·배정 SQL/통합 테스트 |
| B가 사진 수집 후 좋아요 | 서버에 사용자·강아지당 한 건, 중복 요청으로 수 증가 없음, A가 재조회하면 1명 표시 | 다중 사용자 SQL + 독립 A/B 브라우저 |
| B 재접속·좋아요 해제 | 선택 상태 유지→해제하면 A 집계 0명; B의 모은 사진·티켓은 그대로 | A/B 브라우저 + SQL |
| A가 기존 강아지 사진 추가 | 추가분은 검수 전 비공개, 승인해도 기존 사진 ID·수집·하트·보상·SVG 불변, 전체 장수만 증가 | 추가 사진 UI/API/검수/다중 사용자 SQL |
| 무료 2회→0장→광고 | 정상 홈 버튼→강아지 선택→광고 완료→교감→사진; 승인된 보상만 1회 적용 | 정상 앱 모바일 E2E + 실제 Edge + SQL |
| 광고 취소·오류·중복 이벤트 | 취소/오류 무보상, 재준비 가능, 완료 응답 유실은 같은 세션 복구, 중복 차감·보상 없음 | 광고 컨트롤러/앱 통합·브라우저·SQL |
| 자연 충전·일일 경계 | 3시간마다 1장, 최대 2장, 광고가 충전 기준을 밀지 않음, 자정 티켓 리셋 없음 | 시각 제어 SQL/단위 테스트 |
| 교감·사진 준비 | 첫 두 입력 사진 호출 0회, 세 번째 입력 기존 API 1회, 900ms 뒤 모달; 정적 반달 눈웃음·저장 SVG 불변 | PlayScene·버퍼·API/Edge·브라우저 |
| 닫기·느린 응답·사진 실패 | 떠난 화면 재개방 없음, 서버에서 확정된 결과는 재조회로 복구, 재시도 무중복 차감 | 앱 통합·브라우저·SQL |
| 공유 보상 | 서버가 확인한 이벤트만 보너스 반영; 닫기 자체는 보상 아님; 중복·순서 역전·결과 유실 복구 | 공유 SDK/복구·서버 정책·SQL 테스트 |
| 충전 푸시 | 동의한 사용자에게만 자연 충전 예약, 해제/방문/완주 시 취소, 야간 보류·하루 한도·중복 방지 | 알림 SQL + worker/암호화/sender 합성 테스트 |

좋아요는 사진을 터치할 때 나타나는 하트 애니메이션과 별개다. `또 보고 싶어요 / 마음에 담았어요` 버튼의 서버 상태만 집계한다. 현재 다른 사용자의 좋아요를 실시간으로 밀어주는 Realtime 연결은 없다. **등록자 화면 재조회·재진입 후 집계 반영**을 기준으로 확인하며, 열린 화면의 숫자가 즉시 변한다고 안내하지 않는다.

## 3. 하나의 연결된 A/B 검수 시나리오

자동 SQL 여정은 최신 기능 마이그레이션을 격리 DB에 적용해 아래 순서로 실행한다. 운영 개별 강아지 보정 SQL과 네트워크 확장은 제외하며, Storage는 파일 존재 메타데이터 fixture다. 브라우저 A/B 여정은 승인 완료 fixture부터 시작한다. 두 테스트를 운영 등록부터 출시까지 한 번에 검증한 것으로 합쳐 부르지 않는다.

1. A가 사진 2장과 이름을 등록하고 같은 요청을 다시 보낸다. 강아지·업로드 보상은 각각 한 건이다.
2. B와 C는 pending 사진을 가져오거나 좋아요를 만들 수 없다.
3. 운영자가 초안을 저장한다. 아직 pending이며 실제 사진은 B에게 열리지 않는다.
4. 테스트 운영자가 최종 SVG를 명시 확정한다. 입력·DB 저장·공개 문서 SHA가 같다.
5. B가 사진을 수집한 뒤 좋아요를 두 번 설정한다. 집계는 1명이고 C는 B의 수집 권한을 얻지 못한다.
6. 별도 A 세션에서 등록 목록을 다시 조회한다. 집계 1명을 확인한다.
7. B는 새 브라우저 저장소에서도 앨범·좋아요가 남는다. 해제하면 A 재조회에서 0명이다. 수집 사진은 사라지지 않는다.
8. A가 사진을 추가한다. 승인 전 B의 앨범과 공개 외형은 변하지 않는다.
9. 추가 사진만 승인한다. 기존 사진 ID·수집·좋아요·등록 보상·SVG를 보존하며 전체 사진 수가 증가한다. 추가 사진이 자동으로 B의 수집 사진이 되지는 않는다.

관련 코드: [다중 사용자 SQL](../supabase/migrations/multi-user-journey.node-test.mjs), [A/B 브라우저](../tests/e2e/multi-user.spec.ts).

## 4. 푸시 QA — 요청 성공과 실제 도착 구분

자동 테스트는 **예약 SQL → 선점 → 발송 직전 자격 검사 → 수신자 키 복호화 → 실제 sender/응답 판정 → 결과 SQL**까지 연결한다. 마지막 Toss HTTP만 대체하므로 실제 푸시는 보내지 않는다.

- 미동의·해제 사용자는 전송 호출 0회.
- 잔액 0의 자연 충전만 예약. 공유/광고 보상과 1→2 충전은 새 예약 원인이 아니다.
- KST 21시~08시는 보류. 발송 직전 방문·완주·동의·템플릿을 다시 검사한다.
- HTTP 200만으로 `sent`가 되지 않는다. 푸시 성공 상세와 건수를 확인한다.
- 응답 유실은 `unknown`; 자동 재전송해 중복 알림을 보내지 않는다.
- Edge 스위치와 DB cron 스위치 OFF를 모두 확인한다. cron OFF라도 직접 worker 호출은 발송할 수 있으므로 운영 상태 점검용으로 호출하지 않는다.

실기기 단계에서는 사용자가 지정한 A/B 테스트 계정만 사용한다. A 동의·B 거절 → 허용된 테스트 주기 → A 기기 도착 확인 → 링크로 앱 진입 → 새 잔액 확인 → 해제 후 미발송을 확인한다. OS 알림 차단, 앱 종료/복귀, Android/iOS도 구분한다. 테스트 수신자·발송 범위를 정하기 전 운영 알림 스위치를 켜지 않는다.

현재 운영 ON/OFF는 이 자동 실행으로 확인하지 않는다. 과거 문서의 스위치 상태를 현재 상태로 간주하지 않는다. [알림 운영 절차](RECHARGE_NOTIFICATIONS.md).

## 5. 반복 주기와 출시 차단 기준

- 변경마다: 수정 영역 단위 테스트 + 타입 검사.
- 기능 묶음마다: `npm run test:flows` 전체. 실패를 retry로 숨기지 않는다.
- 출시 후보마다: production 웹 빌드 → DB/Edge 버전과 후보 해시 확인 → 정상 앱의 A/B QR 핵심 여정 → 운영자가 확인한 뒤 검토 요청/출시.
- 광고 그룹·알림 템플릿·SDK 버전·인증서/권한을 바꾼 경우 해당 실기기 확인을 다시 수행한다.
- 운영 모니터링은 별도 권한과 일정이 필요하다. 이번 작업으로 정기 실행·푸시·외부 로그 전송을 설치하지 않는다.

다음은 출시 차단 결함이다: 타인 pending 사진 노출, 다른 사용자의 수집 권한 사용, 중복 차감/보상, 등록·수집 기록 소실, 잘못된 최종 SVG, 무동의/중복 푸시, 0장 광고 진입 불가, 닫기 불가.

확인 기록에는 후보 SHA256/deploymentId, 소스 식별값, DB/Edge 버전, 비밀값을 제외한 기능 스위치, 기기/OS/Toss 버전, 시나리오 ID, 예상/실제 결과, 캡처·오류 코드를 남긴다. 원본 익명키·서명 URL 토큰·사용자 사진을 일반 QA 로그에 남기지 않는다.

## 6. 남은 검증 경계

- 실제 Toss SDK 광고 표시·광고 재고·리워드 콜백, 푸시 도착과 알림 링크 진입은 휴대폰 확인이 남는다.
- 전체 신규 등록·검수 조작을 두 브라우저에서 실제 PostgREST/Storage와 연결하는 자동 E2E는 아직 없다. 현재는 등록/검수 HTTP·SQL과 승인 이후 A/B 브라우저로 나누어 검증한다.
- 실제 다중 DB 연결의 동시 요청·트랜잭션 경쟁은 격리 PostgreSQL/Supabase 환경에서 별도 확인해야 한다. PGlite의 순차 실행 통과를 동시성 부하 검증이라고 부르지 않는다.
- 공유 보상/동의창/업로드 사진 선택기의 실제 네이티브 UI는 브라우저 fixture만으로 검증할 수 없다.
- 200% 글자, 스크린리더, 네이티브 내비게이션, 저사양 기기 메모리와 실제 네트워크 지연은 출시 전 수동 체크 항목이다.
