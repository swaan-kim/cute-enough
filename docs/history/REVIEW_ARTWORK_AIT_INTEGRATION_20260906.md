# 검수 확정 이미지 → AIT 연동 점검 · 2026-09-06

## 현재 상태와 권한 경계

- 운영 조회 결과: `pet-api` **24 / ACTIVE**, `pets.reviewed_artwork`가 있는 강아지 **0마리**. 이번 변경은 운영에 배포하지 않았다.
- 기존 이미지 저장 마이그레이션 `20260906000100`의 배포 기록은 [기존 점검 문서](REVIEW_ARTWORK_AUDIT_20260906.md)에 있다.
- 이번에는 강아지 승인·재승인·확정 이미지 저장·운영 DB 변경·AIT 생성/업로드·출시를 수행하지 않았다. 기존 강아지/등록/사진 기록도 변경하지 않았다.
- 현재 검수 초안은 승인된 외형으로 간주하지 않는다. 실제 파일 해시와 Toss 표시 검증은 **사용자가 명시적으로 확정한 한 마리**가 있어야 진행할 수 있다.

## 로컬 구현

### 동일 이미지 표시 및 복구

- `PetArtwork`는 `illustrationUrl` 또는 확정 이미지 메타데이터가 있으면 저장 이미지 경로를 우선한다. 기존 무이미지 강아지만 기존 SVG 렌더러를 사용한다.
- 저장 PNG는 원래 비율(현재 1080×936)을 유지하고 `object-fit: contain`으로 표시한다. 별도의 혀·소품을 덧그리지 않는다.
- 다운로드/서명 실패 때 다른 SVG로 대체하지 않는다. 같은 공간에서 로딩 → 실패 → 다시 불러오기를 제공한다.
- 집과 앨범의 기존 버튼이 실패 시 재시도 버튼 역할을 하므로 버튼 중첩이나 의도치 않은 교감 시작이 없다.
- 메모리 자원은 `pet.id + designVersion + sha256`으로 공유한다. 집·교감·공유·내 강아지·앨범 왕복 시 같은 외형을 유지하고, 이전 응답/이미지 로드 이벤트가 새 결과를 덮지 못한다.
- 서명 URL의 6시간 만료, 앱 복귀, 온라인 복구를 처리한다. 동시 갱신은 하나로 합치며 서명 URL을 로컬 영구 저장하지 않는다. 구버전 URL의 JWT 만료 값은 갱신 시각 힌트로만 사용한다.

### 교감 동작의 차이

- 간식 선택·먹이기·쓰다듬기·완료 후 사진 공개 흐름과 기존 진동 호출은 유지한다. 이미지 로딩/실패 중에는 교감 진행을 잠시 막고, 복구 후 이어간다.
- PNG 전체의 흔들기·먹기·점프 효과는 유지한다.
- **눈·혀·꼬리의 부분 애니메이션은 정적 PNG 안에서 움직이지 않는다.** 저장 시점의 표정이 유지된다. 부분 애니메이션까지 필요하면 별도 승인된 애니메이션 자산 설계가 필요하다.

### API 장애 격리

- `withReviewedArtwork`가 `pet`, `pets`, `dailyPets`, `ownerBonusPet`의 권한 확인된 요약에 이미지 URL·만료 시각·공개 메타데이터를 연결한다. 원본 실사 경로나 별도의 Storage 경로 필드는 추가하지 않는다.
- 개별 서명 실패는 그 강아지만 `illustrationStatus: unavailable`로 반환한다. 정상 강아지, 티켓 상태와 원래 API 응답은 유지한다. 메타데이터 조회 장애처럼 외형을 확인할 수 없는 경우에는 잘못된 재생성 대신 재시도 상태를 사용한다.
- 새 `artwork` 동작은 기존 mTLS 익명키 검증·요청 제한 뒤에서 승인견의 캐릭터 URL만 재발급한다. 실사 사진 공개·티켓 차감 RPC는 호출하지 않는다.
- **운영 버전 24에는 이 새 갱신 동작과 장애 격리가 아직 없다.** 새 앱보다 API 후보를 먼저 배포해야 한다. 운영 배포 시 다른 미커밋 기능을 통째로 덮어쓰지 않도록 이미지 변경 범위를 별도 대조한다.

### 승인 우회와 미연결 파일

- 로컬 후보 `20260906000200_reviewed_artwork_publication_guard.sql`은 승인/디자인 변경 트랜잭션의 최종 상태에서 이미지 존재·디자인 버전·Storage 객체를 검사한다.
- 기존 승인견은 그대로 둔다. 향후 외형 변경은 새 확정 이미지 없이 커밋하지 못한다. 구형 승인/공개 RPC의 직접 service-role 실행 권한도 회수하며, 이미지 포함 래퍼의 내부 호출은 유지한다.
- README와 검수 안내의 구형 직접 승인 예제를 이미지 포함 경로로 정리했다. 운영 SQL 직접 수정/초기 seed 재실행은 이미지 확정 저장의 대체 경로가 아니다.
- `unlinked_reviewed_artwork_candidates`는 24시간 이상 된 파일 중 현재 DB와 과거 이미지 감사 로그 어디에도 연결되지 않은 후보만 보여주는 service-role 전용 **조회**다.
- 이 후보에는 삭제 작업이 없다. 승인 실패/타임아웃 직후 파일을 지우지 않는다. 추후 정리 실행 시에도 DB 연결 여부를 다시 확인해야 한다.

## 검증 결과

- 관련 앱/API 테스트 **82개 통과**: 화면별 이미지 전달, 실패 시 대체 SVG 차단, 재시도, 6시간/복귀/재실행 갱신, 오래된 응답 무시, 교감 완료 유지.
- 검수 서버·PNG 저장·PGlite DB 테스트 **22개 통과**: 원본 업로드 바이트/해시, 실패 시 승인 금지, 원자적 저장, 구형 RPC/직접 SQL 우회 방지, 미연결 후보의 보수적 조회.
- 타입 검사와 웹 preview 빌드/불필요 자산 정리/개발 도구 제외 검사를 수행했다.
- 360px 로컬 브라우저에서 모의 검수 SVG를 메모리 PNG로 만들어 집·교감·공유·내 강아지·앨범을 확인했다. 별도 SVG/혀 레이어 0개, 원본 크기 1080×936, 비율 유지 및 실패 UI를 확인했다. 서버에 모의 이미지를 저장하거나 승인 요청을 보내지 않았다.
- 이것은 로컬 모의 검증이며 **운영 승인 파일과 앱 다운로드 파일의 해시 일치, 실제 Toss 재실행/만료 복구는 아직 미검증**이다.

## 다음 단계 — 별도 확인 후 진행

1. 사용자가 한 마리의 최종 외형을 명시적으로 확정한다.
2. 별도 배포 승인을 받은 뒤 호환 DB 가드 → 이미지 API 후보 → 새 AIT 순서로 배포한다. 다른 기능/운영 스위치는 바꾸지 않는다.
3. 확정 이미지 저장 경로로 그 한 마리만 저장하고 DB 참조·저장 바이트 SHA-256을 확인한다. 이전 승인 기록은 유지한다.
4. 앱 API URL로 받은 실제 파일의 SHA-256과 DB 값을 비교한다.
5. Toss QR에서 집·교감·공유·내 강아지·앨범, 앱 재실행, 장시간/만료, 다운로드 실패→재시도를 확인한다.
6. QR 실기기 검증과 일반 사용자 출시를 구분한다. 이번 문서는 승인이나 배포 권한을 대신하지 않는다.
