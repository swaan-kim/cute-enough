## 잠금과 원자성

초기화에는 고정 advisory 잠금과 단일 실행 행을 사용한다. 한 번 성공한 초기화는 새 UUID로 다시 호출해도 `ALBUM_RESET_ALREADY_APPLIED`로 거절된다. 같은 트랜잭션의 실패·롤백은 실행 표시도 취소한다.

요청 ID 래퍼는 사용자별 잠금을 얻기 **전에** 같은 advisory 키의 공유 잠금을 얻는다. 초기화는 배타 잠금을 즉시 시도하고 진행 중 요청이 있으면 `ALBUM_RESET_BUSY`로 중단한다. 초기화가 실행 중이면 새 래퍼 요청은 만료 표시 생성까지 기다린다.

초기화는 변경·보존 테이블 모두에 `SHARE ROW EXCLUSIVE` 잠금을 획득한 뒤 기준 시각을 정한다. 이는 구버전 v2/v3 등 별도 래퍼가 없는 요청과 등록·검수·보상 변경의 쓰기 잠금과 충돌한다. 읽기는 허용하지만 쓰기가 섞인 요청은 기다릴 수 있다. 초기화 내부에서 사용자별 advisory 잠금을 추가로 얻지 않는다.

기존 요청이 다른 순서의 테이블 잠금을 보유했다면 교착이나 잠금 시간 제한으로 초기화 또는 경쟁 요청이 실패할 수 있다. PostgreSQL이 해당 트랜잭션을 롤백하며 부분 초기화는 커밋되지 않는다. 운영 호출의 외부 트랜잭션에도 `lock_timeout=3s`, `statement_timeout=30s`를 지정한다. 함수의 `SET statement_timeout`만으로 현재 최상위 쿼리 전체 시간을 제한한다고 가정하지 않는다.

여러 HTTP 호출로 나뉜 사진 준비와 기록은 한 트랜잭션이 아니다. 초기화 이전에 준비만 된 요청은 기록 시 기존 RPC가 사진 선택·티켓·권한을 다시 검사한다. 이미 완료된 요청은 만료 표시로 차단된다. 앱에서 진행 중인 화면은 다시 선택이 필요할 수 있다.

## 비공개 보관과 확인

`pet_collection_reset_private` 스키마의 세 테이블에 RLS를 켜고 `public`·`anon`·`authenticated`·`service_role`의 직접 접근을 모두 차단한다. 서비스 역할에는 공개 스키마의 초기화·상태 RPC 실행만 허용한다. 과거 내부 구현 함수의 직접 실행 권한도 없다.

- `runs`: 단일 실행 ID·기준 시각·건수와 SHA-256 확인 결과.
- `archived_rows`: 변경 대상 원본 행을 UTC JSONB로 보관하고 행별 SHA-256을 저장. 추가한 adoption 행도 별도 구분으로 기록한다.
- `request_tombstones`: 이전 요청의 만료 표시. 원래 영수증을 대체하거나 삭제하지 않는다.

반환 JSON은 실행 ID·시각·건수·해시만 포함한다. 사용자 식별값·강아지 ID·사진 경로·원본 행은 반환하지 않는다. 보존 테이블의 전후 SHA-256이 다르면 실패하고 원본 삭제와 보관 작업까지 모두 롤백한다.

## 운영 적용 절차 — 자동 실행 금지

1. 새 파일 `supabase/migrations/20260915000100_album_collection_reset.sql`만 읽고 검토한다. 이 파일에는 reset RPC 호출이 없다.
2. 승인된 단일 파일만 적용한다.

```powershell
npx --no-install supabase db query --linked --file supabase/migrations/20260915000100_album_collection_reset.sql
```

3. 설치 성공을 `to_regprocedure`와 권한 조회로 확인한 뒤 새 버전 **20260915000100 하나만** 마이그레이션 이력에 기록한다. 수동 단일 파일 적용은 자동으로 이력을 남기지 않는다. CLI의 특정 버전 repair를 이용할 때도 기존 이력은 수정하지 않는다.

```powershell
npx --no-install supabase migration repair 20260915000100 --status applied --linked
```

`db push`를 사용하면 미적용된 다른 파일까지 적용될 수 있다. 이 작업과 관계없는 `20260912000100_photo_prepare_rate_limit.sql`을 함께 적용하지 않는다. 마이그레이션 이력의 전후 차이는 새 버전 하나여야 한다.

4. 초기화 RPC 실행 전 다음 읽기 결과를 확인한다.

```sql
select count(*) as unlocks, count(distinct owner_hash) as collectors
from public.user_photo_unlocks;
select public.get_pet_album_collection_reset_status();
```

상태가 `null`일 때만 첫 실행을 진행한다. 이미 결과가 있으면 재실행하지 않는다.

5. 별도 SQL 파일에 확인한 UUID와 최신 집계를 넣어 **한 번의 DB 호출**로 실행한다. 아래 대문자 자리표시는 실제 검토한 값으로 치환해야 하므로 그대로는 실행되지 않는다.

```sql
begin;
set local lock_timeout='3s';
set local statement_timeout='30s';
select public.reset_all_pet_album_collections(
  'REVIEWED_RESET_UUID'::uuid,
  VERIFIED_UNLOCK_COUNT,
  VERIFIED_COLLECTOR_COUNT,
  'RESET_ALL_USER_ALBUMS_KEEP_REGISTERED_DOGS'
);
commit;
```

서비스 역할의 REST RPC로도 호출할 수 있지만 이 운영에서는 위 외부 트랜잭션 제한을 포함한 CLI SQL 호출을 사용한다. DB 함수가 요청 중인 사용자 대신 임의 익명키를 만들거나 광고를 대신 시청하지 않는다.

6. 응답 유실은 실패로 단정하지 않는다. 상태 RPC와 집계를 다시 읽어 커밋 여부를 판단한다. 반환된 `preservationVerified=true`, 전후 보존 해시 일치, 보관 행별 해시, 원본 사진 건수, 빈 도감 권한, 남은 티켓·미사용 광고 보상을 확인한다. 실패한 RPC가 `ALBUM_RESET_BUSY`·`ALBUM_RESET_COUNTS_CHANGED`·잠금 시간 초과를 반환하면 원인을 해소하고 최신 집계로 다시 검토한다.

## 복원과 앱 캐시

전체 작업은 명시적 `BEGIN` 안에서 실행 후 `ROLLBACK`하면 원래 상태로 돌아간다. 커밋 이후에는 비공개 보관본을 사용해 복원용 **후속 마이그레이션/운영 SQL**을 별도로 검토한다. 이미 적용한 파일이나 마이그레이션 이력을 삭제하지 않는다.

새 수집이 발생했다면 보관된 사진 권한은 `ON CONFLICT DO NOTHING`으로 합치는 방향이 필요하다. 새 일일 수집·재열람 기록, 새 티켓 차감, 새 광고 소비와 현재 집 진행을 덮어쓰지 않는다. 초기화 후 새 활동이 있는 상황에서 이전 전체 스냅샷을 덮어쓰는 방식은 금지한다. adoption과 요청 만료 표시는 재지급·중복 차감을 막으므로 임의 제거하지 않는다. 완전한 원상복원과 새 활동을 보존하는 병합 복원은 다른 작업이다.

앱의 도감 목록 캐시는 5분이고 이미 발급된 사진 URL은 10분 유효하다. 열려 있는 사진이나 내려받은 이미지를 DB 초기화로 즉시 회수할 수 없다. 앱을 다시 열면 빈 도감을 불러오며, 기존 화면의 이전 요청은 만료될 수 있다. 서버 영수증은 보존되어 재시도로 티켓을 다시 차감하지 않는다.
