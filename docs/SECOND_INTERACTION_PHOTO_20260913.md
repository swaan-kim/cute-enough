# 두 번째 교감부터 사진 준비 · 2026-09-13

[세 번째 입력 방식](THIRD_INTERACTION_PHOTO_20260913.md)의 후속 개선이다. 마지막 900ms보다 서버·다운로드가 오래 걸릴 수 있어 요청 시작만 두 번째 입력으로 당긴다. 화질·사진 크기·모달 배치·교감 횟수는 바꾸지 않는다.

## 사용자에게 달라지는 점

- 간식·첫 입력: 사진 API 호출 없음.
- 두 번째 유효 입력: 기존 공개·소유자 사진·무료 재열람 중 해당 API를 한 번 호출하고 같은 이미지 버퍼로 다운로드·디코딩한다.
- 세 번째 입력: 기존 900ms 반달 눈웃음·꼬리 반응 후 사진창을 연다. 먼저 준비되어도 세 번째 전에는 표시하지 않는다.
- 유료 안내: `두 번째로 쓰다듬으면 티켓 1장으로 사진을 준비해요`.
- 두 번째 이후 나가도 서버에서 확정된 수집·차감은 남는다. 재진입 때 무료 재열람할 수 있으며 중간 이탈은 교감 완료로 집계하지 않는다.
- 떠난 뒤 API 응답 자체가 실패해도 수집 확정 여부를 단정하지 않고 집·앨범 상태를 다시 확인한다. 이미 받은 사진의 다운로드 취소에는 불필요한 추가 재조회를 하지 않는다.
- 아직 느린 사진은 같은 창에서 로딩·재시도한다. 모든 네트워크 대기가 사라진다고 보장하지 않는다.

## 서버 처리

권한 확인 → 사진 선택 → 서명 URL 발급 → 수집/차감 기록 → 경쟁 요청의 확정 사진 재확인은 순서대로 유지한다. 그 뒤의 앨범 상태와 티켓·보상 조회만 병렬화한다. 두 실패를 모두 회수하며 기존 앨범 오류 우선순위를 유지한다.

날짜가 다른 수집 재시도는 앨범 상태 → 오늘 진행도 갱신 → 보상 상태 순서를 유지한다. 구버전 재열람은 기존 후속 조회를 유지한다. 사진 선택·요청 ID·하루 한 장·광고 완료 보상·무료 재열람·원자적 차감 정책은 바꾸지 않는다.

## 운영 배포 범위

- 프로젝트 `xoqjehiqbaxpalbghngm`, `pet-api` **29 → 30**, ACTIVE 확인.
- 배포 직전 29번 소스를 내려받아 비교했다. `album-api.ts`와 `index.ts`의 후속 조회 병렬화, 이전에 고친 내 사진 서명 성공 후 열람 기록 순서만 적용했다.
- 아직 운영에 없는 별도 `photoPrepare` API/허용 action/오류 분기는 제외했다. 클라이언트도 호출하지 않는다. 따라서 이번 DB 마이그레이션은 없다.
- 기존 CORS·mTLS·요청 제한·광고/공유/알림 스위치와 비밀값은 그대로다. 알림 함수는 5번으로 변하지 않았다.
- 실제 배포용 처리기의 Deno 타입 검사와 외부 네트워크를 차단한 8단계 검사를 별도로 통과했다.
- 배포 후 소스를 다시 내려받아 23개 의존 파일의 SHA256이 준비본과 전부 같은지 확인했다.
- 허용된 네 Toss Origin의 OPTIONS 204/정확한 Origin 반환, 임의 Origin·null의 403, 식별값 없는 POST의 400을 확인했다. 실제 사진 수집·광고·푸시·강아지 승인은 실행하지 않았다.

배포 파일 SHA256:

| 파일 | SHA256 |
| --- | --- |
| `pet-api/index.ts` | `115eb71c087baf2aca00bc820bfcd7150f6e14b279a61334a050dfa5d427ecbe` |
| `pet-api/album-api.ts` | `5180a24907fb0028d6fae14ed5d6a798021e0a0cd0f89eebafd7632caf8cfb34` |

로컬 전체 처리기에는 미배포 `photoPrepare` 호환 코드가 남아 있어 운영 `index.ts` 해시와 다르다. 운영 30번 재현은 29번 다운로드본에 위 두 파일의 해당 변경만 적용하는 방식이다. 이후 전체 Edge를 배포할 때 준비 API의 DB 호환을 별도로 확인한다.

지연 비교는 390px에서 한 번 수행하므로 다른 두 폭의 동일 비교는 의도적으로 제외한다. 기능 검사는 세 폭 모두 수행한다. 두 번째 후 이탈·지연 응답·무료 재방문, 광고 취소/실패/중복 보상, 소유자/무료 재열람, A/B 좋아요와 기존 수집 보존을 확인했다. 360px 실제 캡처에서 새 안내와 반달 눈웃음도 확인했다.

검사 도중 산책 중인 강아지가 겹쳐 다른 친구를 터치하는 테스트 선택자 문제가 있었다. 새 이탈 검사의 재진입은 대상 강아지의 접근성 버튼으로 지정하고 교감은 실제 터치 입력으로 유지했다. 앱 배치나 산책을 변경하지 않았으며, 최종 전체 검사는 자동 재시도 없이 통과했다.

로컬 브라우저에서 요청 시작/API 응답/다운로드/디코딩/화면 표시를 각각 측정한다. 측정 코드는 테스트 fixture에만 있으며 운영 앱에는 추가하지 않는다. 실기기 Toss 성능·광고 재고·푸시 도착 검증과 구분한다.

별도 390px 비교 실행에서는 1,500ms 다운로드 지연과 650ms 입력 간격을 설정했을 때 세 번째 입력부터 사진 표시까지 1,547.4 → 911.9ms로 줄었다(635.5ms 감소). 이전 조건은 테스트에서 요청 시작점만 세 번째로 돌린 것이며, 1px PNG·가짜 API를 쓴 로컬 Chromium 결과다. 실제 사진 크기·mTLS·운영 서버 왕복이나 휴대폰의 성능 수치가 아니다.

새 후보는 `AIT/LATEST/cute-enough.ait`, 소스 식별값·런타임·플래그·SHA256·크기·deploymentId는 같은 폴더 `release.json`을 기준으로 전달한다. 이번 범위에 Toss 업로드·검토 요청·일반 사용자 출시는 포함하지 않는다.
