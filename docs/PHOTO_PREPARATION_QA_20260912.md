# 광고 정상 흐름·교감 중 사진 준비 작업 기록

## 이번 구현

- 간식 먹기 뒤 쓰다듬기 시작 신호와 세 번째 입력의 완료 신호를 분리했다. 터치/쓰다듬기/키보드 총 3회, 72px 쓰다듬기 판정, 마지막 450ms 눈웃음·점프·꼬리 반응은 유지한다.
- 내 사진·이미 수집한 사진만 쓰다듬기 시작 때 `photoPrepare`로 준비한다. 수집·티켓·광고·방문/재열람 기록과 legacy 선물 초기화를 하지 않는다. 요청 제한 카운터만 갱신한다.
- 새 사진은 세 번째 유효 입력 직후 기존 공개 요청을 시작한다. 서버의 권한·차감 확정 후에만 이미지가 도착하며 마지막 반응 시간과 요청/다운로드를 겹친다. 첫 번째 입력부터 미수집 원본을 미리 내려주지 않는다.
- 준비한 사진은 최종 공개 응답의 `photoId`와 같을 때만 재사용한다. 사진 설명과 차감 상태는 최종 응답을 따른다. 준비 실패·선택 변경·만료 시 최종 URL을 새로 읽는다.
- 한 교감 동안만 Blob URL을 보유한다. 사진을 다운로드·디코딩한 뒤 표시하고, 이동/닫기/백그라운드에서 불필요한 준비를 취소한다. 사용하지 않은 준비본은 5분이 지나면 자동 해제한다. 최종 권한 확인 뒤 표시 중인 사진은 닫을 때까지 유지한다. 다운로드 12초 제한·8MB 상한·이미지 MIME 확인을 적용하며 영구 실사 캐시는 만들지 않는다.
- 느린 회선에서는 사진창 안에 기존 로딩/재시도를 유지한다. 모든 네트워크에서 즉시 표시된다는 보장은 아니다.
- 정상 앱 E2E에서 찾은 개발 StrictMode 첫 집 조회 취소 후 미재시작을 수정하고, 오래된 응답이 새 집을 덮지 않는 검증을 추가했다.
- preview의 사진 준비도 legacy 선물 이관을 실행하지 않도록 읽기 전용으로 맞췄다.
- 반복 회귀에서 기존 앨범 SQL 테스트가 앞선 사진 교체/비활성 테스트의 강아지를 무작위로 골라 실패하던 문제를 재현했다. 3장 수집 검사에 독립된 강아지·배정을 만들도록 테스트 fixture만 수정했고, 해당 18개 검사를 독립 실행 5회 연속 통과했다. 운영 광고 정책은 이 수정으로 바꾸지 않았다.

## 배포가 필요한 부분

1. `20260912000100_photo_prepare_rate_limit.sql`: 현재 허용 목록에 `photoPrepare`만 추가하며 기존 카운터와 액션을 보존한다. 실제 SQL 테스트에서 목록 누락 시 요청이 실패함을 재현했다.
2. `pet-api`: 읽기 전용 준비 동작과 30회/분 제한. 소유자 pending/approved 또는 타인 approved의 기존 수집 사진만 허용한다. 권한 실패 때 보상 복구 조회가 부수적으로 실행되는 것도 차단했다.
3. 앱: PlayScene/App 사진 준비·완료 시점 연결 및 취소 복구.

순서는 **후속 DB 마이그레이션 → Edge → 새 앱 후보**다. 이 작업에서는 운영 DB 적용·Edge 배포·AIT 생성/업로드·검토 요청·출시·강아지 승인을 하지 않았다. 서버가 준비 API를 아직 지원하지 않아도 준비 실패는 조용히 무시하고 최종 공개 경로로 진행한다.
