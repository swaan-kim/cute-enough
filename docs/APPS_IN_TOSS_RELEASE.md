# 앱인토스 제출 체크리스트

이 문서는 `appName: cute-enough`, 콘솔 노출명 `옆집 강아지`의 비공개 QR 검수와 제출 순서를 기록합니다. `귀엽기만 해도 되나요?`는 앱 내부 슬로건이며 서비스명으로 혼용하지 않습니다. Vercel은 샘플 데이터 화면 확인용이고 제출 판정에 사용하지 않습니다.

## 1. 외부 연결 전 확인

기존 운영 설정과 연결 상태를 먼저 확인하고, 이미 완료한 설정은 그대로 사용합니다.

- Supabase 프로젝트 요금제·Storage/Edge Function 예상 사용량 확인
- 앱인토스 익명키 검증용 mTLS 인증서와 개인 키 발급
- 활성 실사 사진과 검수 기록이 있는 기존 승인 강아지 후보 확인
- 사업자·정산·리워드 광고 그룹 승인과 실광고 그룹 ID 확인
- 영구 공개 저장소에 1200×600 공유 OG 이미지 업로드

자동 OpenAI API는 사용하지 않습니다. 승인 대기견은 운영자가 개별 수정할 예정이므로 이 배포를 위해 수정하거나 승인하지 않습니다.

## 2. Supabase 적용

운영 프로젝트 `xoqjehiqbaxpalbghngm`과 마이그레이션 이력·실제 함수 정의를 대조한 뒤 필요한 SQL만 적용합니다. 수동 적용한 정확 일치 SQL은 내용 확인 후 이력을 맞춥니다. 이 저장소의 과거 개별 강아지 데이터 수정 SQL을 이력에 없다는 이유로 재실행하지 않습니다. 무조건적인 `db push` / `--include-all`은 사용하지 않습니다.

```bash
supabase link --project-ref <PROJECT_REF>
# 운영 이력과 대조한 필요한 마이그레이션만 순서대로 적용
supabase functions deploy pet-api --no-verify-jwt
supabase functions deploy recharge-notifications --no-verify-jwt
```

`pet-api`는 클라이언트 JWT 대신 앱인토스 익명키를 mTLS로 검증합니다. 다음 값은 Supabase secrets로만 저장하고 `VITE_` 변수나 Git에 넣지 않습니다.

```text
AIT_RUNTIME_ENV=production
AIT_MTLS_CERT_PEM=<PEM 원문>
AIT_MTLS_PRIVATE_KEY_PEM=<PEM 원문>
USER_HASH_SALT=<충분히 긴 무작위 값>
AIT_REWARDED_ADS_ENABLED=false
AIT_SHARE_REWARDS_ENABLED=false
RECHARGE_NOTIFICATIONS_ENABLED=false
AIT_UPLOADS_ENABLED=true
AIT_DAILY_UPLOAD_LIMIT=25
AIT_PENDING_UPLOAD_LIMIT=100
```

광고, 친구 초대 보상, 충전 알림은 각각 독립적으로 중단할 수 있습니다. 아래 설정을 확인한 뒤 해당 기능을 QR에서 검증합니다. 이미 지급한 공유 보너스와 광고 보상은 중단해도 보존합니다. CORS의 추가 로컬 origin은 운영 환경에 설정하지 않습니다.

| 기능 | 클라이언트/서버 설정 | DB 설정 |
| --- | --- | --- |
| 신규 광고 시작 | `VITE_ADS_ENABLED`, 승인된 `VITE_REWARDED_AD_GROUP_ID`, `AIT_REWARDED_ADS_ENABLED` | `pet_reward_settings.ads_enabled` |
| 친구 초대 보상 신규 적립 | `AIT_SHARE_REWARDS_ENABLED`, SDK 지원 여부, 서버 capability | `pet_reward_settings.share_enabled` |
| 충전 알림 | `RECHARGE_NOTIFICATIONS_ENABLED`, 승인된 동의문/템플릿, mTLS·암호화·cron secrets | `recharge_notification_worker_config.enabled` 및 Vault secret |

공유 모듈은 `e5de3e72-cbfb-4b50-a050-9fd71fb4368b`입니다. 콘솔에서 앱 소속, 단위 `강아지 티켓`, 친구당 수량 `1`을 확인합니다. 충전 알림의 세부 설정은 [충전 알림 운영](RECHARGE_NOTIFICATIONS.md)을 따릅니다.
업로드는 서버에서 하루 전체 25장, 전역 검수 대기 100장, 사용자별 하루 1장·검수 대기 3장으로 다시 제한합니다. 초기 운영에서 사용량을 확인하기 전에는 더 큰 값으로 올리지 않습니다.

현재 앱은 기기에서 JPEG 1024px 이하로 재인코딩하고 밝기·주요 색상만 제안합니다. 강아지 여부와 실제 공개 여부는 운영자가 검수합니다. 이번 보상 기능 배포는 기존 강아지 데이터나 다른 Edge Function을 임의로 삭제하지 않습니다.

## 3. 운영 강아지 확인

- 기존 승인견의 private Storage 사진과 검수 기록을 확인합니다. 출시를 위해 승인 대기견을 승인하거나 사진을 새로 덮어쓰지 않습니다.
- 공개 URL을 만들지 않습니다. 사진 공개 시 `pet-api`가 짧은 만료 시간의 서명 URL만 반환하는지 확인합니다.
- 개발용 Unsplash 샘플 URL은 제출 데이터에 사용하지 않습니다.
- 후보가 4마리보다 적을 때는 복제하지 않고 빈 슬롯을 안내 상태로 표시합니다. 본인 강아지는 공개 후보에서 제외하고 별도 보너스 자리에 표시합니다. 승인견 수를 늘리는 검수 작업은 운영자가 별도로 진행합니다.

## 4. 비공개 QR 빌드

`.env.private.local` 또는 CI 비밀변수에 아래 값을 연결합니다.

```text
VITE_APP_RUNTIME=private
VITE_SUPABASE_URL=https://<PROJECT_REF>.supabase.co
VITE_SUPABASE_ANON_KEY=<SUPABASE ANON KEY>
VITE_ADS_ENABLED=false
VITE_REWARDED_AD_GROUP_ID=
VITE_SHARE_OG_URL=https://<PERMANENT PUBLIC HOST>/share-og.png
```

```bash
npm ci
npm test
npm run test:review
npm run typecheck
npm run build:private
```

생성된 `cute-enough.ait`를 콘솔에 올리고 Toss QR에서 확인합니다.
비공개 공유 링크는 최초 QR 실행 스킴의 `_deploymentId`를 자동으로 보존하므로, 앱을 반드시 해당 배포의 QR로 연 뒤 공유를 시험합니다.

## 5. Toss QR 필수 시나리오

- 최초 실행에서 기본 이용권 2개가 보이고 두 강아지를 광고 없이 만날 수 있음
- 홈에 `무료 2/2 · 보너스 N장`이 표시되고, 무료 만충·오늘 공개견 완료 상태에서도 친구 초대 보너스를 적립할 수 있음
- 기본 이용권을 쓰면 3시간 뒤 1개씩 충전되며 최대 2개를 넘지 않음
- 같은 사용자·같은 KST 날짜에는 공개 강아지 4마리의 구성과 순서가 유지되고, 자정 뒤 새로운 목록으로 교체됨
- 최신 본인 `pending | approved` 강아지가 있으면 공개 4마리와 중복되지 않는 소파 전용 다섯 번째 친구로 표시됨
- 내 강아지는 이용권·광고·공개 `4/4` 진행도를 사용하거나 증가시키지 않고 사진을 바로 열 수 있음
- 공개 후보가 부족한 경우 강아지를 복제하지 않고 `새 친구를 기다리고 있어요` 슬롯을 표시함
- 광고 미승인 상태에서는 이용권이 없을 때 광고 UI가 보이지 않음
- 사진 허용, 거부, 취소, 권한 철회, 미지원 앱 버전 안내
- 이름 4글자 제한, 제로폭·제어문자·금칙어 차단
- 업로드 직후 내 강아지가 보너스 자리에 등장하고 `pending` 상태에서도 소유자만 사진을 바로 열 수 있음
- pending 공유 수신자는 캐릭터만 보고 사진·광고·일일 횟수는 사용하지 않음
- approved 공유 수신자는 최신 이용권 상태에 따라 입장
- 네 번째 공개 사진 안에서 `오늘의 네 번째 친구 · 4/4`가 보이고, 사진창을 닫아 홈으로 돌아왔을 때 완료 안내가 하루 한 번만 표시됨
- 재접속 시 완료 Toast를 반복하지 않고 홈 카드만 `4/4` 상태를 유지함
- 사진 저장은 원본 URL이 아니라 기존 분홍 로고와 해당 강아지 이름표를 합성한 JPG만 전달하며, Android 5.218.0·iOS 5.216.0 이상에서 `File.saveBase64`로 기기에 저장
- 기존 등록 사진은 워터마크 저장 동의를 소급하지 않는다. 소유자 확인 후 `consent_version`을 갱신한 사진만 운영 저장 대상으로 사용
- 네이티브 뒤로가기: 모달 → 이전 앱 화면 → 루트에서 토스로 복귀
- 네이티브 홈: 어느 화면에서든 홈 스택으로 초기화
- KST 자정은 공개 강아지 목록과 광고 일일 횟수만 새 날짜로 전환하고, 기본 이용권을 임의로 2개 지급하지 않는지 확인
- 공유 보너스는 자정에 초기화되거나 자동 소멸하지 않으며, 무료 이용권의 2개 상한과 별도로 유지됨
- 다음 무료 이용권 충전 전 이미 만난 강아지를 다시 누르면 이용권 차감과 간식 과정을 건너뛰고 같은 실제 사진이 바로 열리는지 확인
- 내 `pending`·`approved` 강아지는 충전 시각과 관계없이 소유권 확인 후 무료로 바로 열리는지 확인
- 오프라인·서버 지연·CORS 차단 시 가짜 성공이나 보상 없음
- 화면 재시도 시 이전 요청이 취소되고 늦은 응답이 최신 공개·진행도 상태를 덮지 않음
- 360×640, 390×844, 430px 및 글자 크기 200%에서 공개 4마리와 내 강아지를 포함한 최대 5마리 배치, 사진창 버튼, Safe Area가 겹치지 않음

2026-09-04 production 측정에서 초기 JS는 `431.61KB gzip`, `.ait`는 약 `1.20MB`입니다. Supabase 전체 클라이언트 대신 Functions 전용 클라이언트를 사용하고 놀이·사진·등록·내 강아지·공유 화면을 지연 로딩했습니다. 현 TDS 의존성을 유지한 상태에서는 초기 JS `350KB gzip` 목표가 아직 남아 있으므로, 앱인토스 용량 기준 통과와 별개로 다음 성능 작업에서 TDS 사용 범위와 공통 청크를 다시 점검합니다.

광고 승인 후에는 실광고 그룹 ID를 넣고 클라이언트와 서버의 광고 플래그를 함께 켠 뒤 다음을 추가로 검수합니다.

현재 앱인토스 SDK의 `userEarnedReward` 이벤트는 클라이언트 콜백이며 독립적인 서버 검증 서명이 아닙니다. 서버 세션과 요청 ID로 중복 처리를 방지하고 Toss QR에서 실제 완료·취소·복구 동작을 검증합니다.

- 광고 안내창에서 취소 가능
- 무료 이용권과 공유 보너스가 모두 0개일 때만 `광고 보고 이 친구 만나기`가 표시되고 오늘 남은 횟수와 다음 자연 충전 시각이 함께 보임
- 광고가 로드된 경우에만 확인 CTA 활성화
- 광고 시작 전에 서버 세션을 만들고, `userEarnedReward` 즉시 보상을 기록함. 광고창 종료를 지급 조건으로 사용하지 않음
- 완료 전 취소·재생 실패는 보상과 일일 한도를 차감하지 않음. 중복 완료 이벤트·응답 유실 재시도는 기존 보상만 반환함
- 광고 완료를 기준으로 하루 최대 2회를 계산하고, 광고 중 무료 티켓이 충전되어도 완료 보상과 자연 충전된 티켓을 모두 보존함
- 광고 공개 뒤에도 이미 진행 중이던 3시간 자연 충전 시각이 유지됨
- 광고 전 소리 중지, 복귀 후 사용자의 음소거 설정 복원

친구 초대 보상과 충전 알림도 별도로 확인합니다.

- 연락처 초대의 `sendViral` 보상만 적립하고 일반 공유창·개별 강아지 링크 복사·취소에는 적립하지 않음
- 여러 친구의 실제 보상 수량을 반영하고 `close` 집계 불일치는 추가 지급 없이 확인 상태로 남김
- 친구마다 1장을 적립하며 발신자에게 별도의 하루 1장 제한을 두지 않음
- 유효한 재열람·내 강아지 → 해당 강아지 미사용 광고 보상 → 무료 이용권 → 공유 보너스 → 새 광고 순서가 유지됨
- 공유 보너스 차감, 사진 접근, 공개 진행도를 한 트랜잭션으로 처리하고 같은 요청 ID 재시도에서 중복 차감하지 않음
- 공유 보상 콜백 수신 후 앱 종료·응답 유실을 복구하되, 콜백 수신 전에 앱이 종료된 사건까지 자동 복구됐다고 표시하지 않음
- 충전 알림 동의·해제, 자연 0→1 충전, 야간 보류, KST 하루 1회, 방문·오늘 완료 시 제외, 불명확한 발송 결과의 중복 방지를 확인함
- 실제 친구에게 임의 초대를 보내지 않으며 실제 알림 테스트도 사용자가 지정한 수신자로만 수행함

## 6. 호환 배포 순서

기존 라이브 앱을 깨뜨리지 않도록 아래 순서를 지킵니다.

1. 출시본 `20260903-21`의 deploymentId `01a065f2-ec98-797c-aa9c-55143c1ed436`과 현재 작업 트리·운영 DB를 비교합니다. 다른 창의 미커밋 변경을 보존합니다.
2. 정확 일치·공개 4마리·보상 원장·알림·등록 재시도 마이그레이션을 실제 운영 이력과 대조해 필요한 것만 적용합니다. 새 기능 스위치는 검증 전까지 꺼 둡니다.
3. 기존 주요 액션과 `apiVersion: 2` 호환성을 유지하는 `pet-api`, 별도 알림 worker를 배포합니다. DB와 함수 배포 결과를 따로 기록합니다.
4. 자동 검증을 통과한 동일 제출 후보 AIT를 업로드하고 새 QR을 생성합니다. 광고·공유 모듈 설정을 확인한 뒤 해당 기능을 실기기에서 검증합니다.
5. A 업로드 → A 즉시 확인 → B pending 공유 → 운영자가 별도로 승인한 뒤 동일 링크 갱신 → 다음 KST 날짜의 공개 후보 편입을 검증합니다. 배포 작업자가 대기견을 대신 승인하지 않습니다.
6. QR 검증을 마친 동일 AIT와 실제 기능을 담은 미리보기·설명문을 확인한 뒤 심사를 요청하고 출시합니다. 업로드, QR 테스트 완료, 심사 요청, 승인, 출시를 별도 상태로 기록합니다.

- 부제, 상세 이용 흐름, 비게임 카테고리
