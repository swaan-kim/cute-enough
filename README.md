## 설계에서 고민한 부분

### 1. 검수한 모습과 앱 속 강아지가 달라지는 문제

처음에는 귀 모양과 털색, 소품 같은 설정값으로 캐릭터를 그렸습니다. 그런데 검수하면서 강아지마다 장식이나 도형을 조금씩 고치자, 기존 설정만으로는 그 모습을 재현할 수 없었습니다. 강아지 ID별로 예외 코드를 넣을 수도 있었지만, 그렇게 하면 외형 하나를 고칠 때마다 앱도 다시 배포해야 했습니다.

검수 결과를 PNG로 저장하는 방법도 고려했습니다. 모습은 그대로 남길 수 있지만, 쓰다듬을 때 눈이 웃거나 꼬리가 흔들리는 반응을 넣기 어려웠습니다. 외형을 보존하면서 부위별로 움직일 수 있어야 했기에 SVG 도형을 저장하기로 했습니다.

현재는 검수자가 확정한 도형을 `PetDesignV1` 문서로 저장하고, 검수 화면과 앱에서 같은 `PetDesignSvg` 렌더러로 그립니다. 지원하는 도형 안에서의 수정은 데이터만 바꾸면 됩니다. 새로운 도형이나 모션을 추가할 때는 앱 배포가 필요합니다.

검수 화면에서는 실사 사진 옆에 64·114·190px 캐릭터를 함께 놓았습니다. 크게 볼 때는 괜찮던 장식도 작은 화면에서는 잘 보이지 않을 수 있어서입니다. 외형을 고치면서 크기별 모습을 비교하고, 꼬리나 혀의 움직임도 같은 화면에서 확인할 수 있게 했습니다.

이미 승인한 강아지도 검색해서 같은 화면에서 고칠 수 있습니다. 다만 수정 중인 모습이 사용자에게 바로 보이면 안 되므로 초안 저장과 공개 확정을 나눴습니다. 공개를 확정하기 전까지 앱에는 기존 모습이 남고, 사용자가 처음 요청한 설정도 최종 디자인과 따로 보관합니다.

대신 문서의 버전과 호환성을 관리해야 했습니다. 저장한 문서와 앱에 도착한 문서가 같은지 SHA-256으로 확인합니다. 같은 문서라도 CSS나 렌더러가 바뀌면 다르게 보일 수 있어 렌더링 테스트도 함께 둡니다. 문서를 읽을 수 없을 때는 재시도를 안내합니다.

### 2. 사진 ID가 없던 시절의 기록

처음에는 사용자가 어떤 강아지를 봤는지만 기록했습니다. 앨범을 만들고 한 강아지에 여러 사진을 등록할 수 있게 되면서, 이제는 어떤 사진을 봤는지까지 알아야 했습니다.

과거 기록에는 사진 ID가 없어 당시 본 사진을 정확히 복원할 수 없었습니다. 그렇다고 기존 사용자의 앨범을 비워 두기도 아쉬웠습니다. 이전에 만난 승인견의 현재 대표 사진을 한 장씩 선물하고, 새로 모은 사진인 `reveal`과 구분해 `legacy_gift`로 기록했습니다.

구버전 앱이 남기는 기록도 고려해야 했습니다. DB를 전환한 뒤에도 구버전에서는 사진 ID 없는 만남이 계속 생길 수 있기 때문입니다. 전체 이관을 한 번 진행한 뒤, 사용자가 새 버전으로 처음 접속할 때 빠진 이력을 보충하도록 했습니다. 이관 여부를 따로 기록해 재접속하거나 요청을 다시 보내도 같은 선물을 중복 지급하지 않습니다.

이후 사진을 교체할 때는 새 ID와 Storage 경로를 발급합니다. 그래야 모아 둔 사진이 어느 날 다른 사진으로 바뀌지 않습니다. 공개가 중지된 사진은 볼 수 없지만 이관 기록은 남겨, 그 자리에 다른 사진이 다시 지급되는 일을 막았습니다.

### 3. 디퍼드 딥링크와 인앱 브라우저 대응

공유에는 토스가 제공하는 디퍼드 딥링크를 사용합니다. 앱이 없는 사람도 설치를 거쳐 원래 목적지로 이동할 수 있는 방식입니다. 그런데 아이폰의 네이버 블로그 앱에서 댓글의 링크를 누르면, 토스가 이미 설치되어 있어도 앱스토어로 연결됐습니다. 같은 링크가 다른 곳에서는 정상적으로 열렸습니다.

리다이렉트를 따라가 보니 공유 링크는 미리보기 페이지와 OneLink를 거쳐 토스 실행을 시도하고 있었습니다. 네이버 User-Agent로 받은 응답에는 페이지가 계속 보이면 잠시 뒤 앱스토어로 보내는 fallback 코드가 있었습니다. 앱 실행이 막히거나 늦어져도 미설치 사용자와 같은 경로로 보내질 수 있었습니다. 이번에 막힌 구간은 설치된 토스로 전환하는 단계였고, 이 응답만으로 실기기의 차단 원인까지 확정할 수는 없었습니다.

단축 링크를 경유한 실험에서는 중간 페이지의 버튼을 직접 누르자 토스가 열렸습니다. 이 결과를 보고 자동 리다이렉트와 사용자 클릭을 구분해 대응하기로 했습니다. 토스가 열리기 전의 문제라 미니앱 내부 라우팅을 수정하는 것으로는 이 경로를 바꿀 수 없었습니다.

우회 방법으로 중간 페이지에서 앱 실행을 한 번 시도하고, 열리지 않으면 사용자가 버튼을 누를 수 있게 했습니다. 항상 클릭을 요구하면 정상 환경에서도 한 단계가 늘어나고, 자동 이동만 두면 실패했을 때 할 수 있는 일이 없어서 두 방법을 함께 뒀습니다.

버튼은 URL scheme을 바로 여는 일반 링크로 만들었습니다. 클릭과 실행 사이에 비동기 작업을 넣지 않아 사용자 입력에 이어 앱을 열도록 했습니다. 앱에서 돌아오면 자동 실행을 반복하지 않고, 시간이 지나도 스토어로 보내지 않습니다. 페이지에 남아 있다는 사실만으로 설치 여부를 알 수는 없기 때문입니다.

중간 페이지는 배포했고 자동 실행과 복귀 동작을 검사했습니다. 기존 단축 링크의 버튼 실행은 실기기에서 확인했지만, 새 우회 방식의 네이버 iOS 앱 전환은 아직 검증 전입니다. 이 방식은 설치된 앱을 여는 보조 수단이며, 개별 강아지 공유와 설치 후 목적지 복원은 기존 디퍼드 딥링크가 담당합니다.

[AppsFlyer의 iOS 앱 전환 제약](https://support.appsflyer.com/hc/en-us/articles/115002366466-URI-scheme-fallback-for-iOS)

### 4. 닫은 사진창에 뒤늦게 도착한 응답

사진을 불러오는 동안 사용자가 창을 닫을 수 있습니다. 그런데 서버에서는 이미 사진 수집과 티켓 차감이 끝났고, 그 응답이 뒤늦게 도착한다면 어떻게 처리해야 할까요?

응답을 그대로 반영하면 닫은 사진창이 다시 열립니다. 응답을 전부 버리면 홈에는 차감 전 티켓이 남습니다. 사진창을 닫았다고 서버에서 끝난 작업까지 취소되는 것은 아니었습니다.

사진을 보여주는 일과 티켓 상태를 갱신하는 일을 나눴습니다. 이미 떠난 화면의 사진은 띄우지 않되, 서버에서 확정된 차감은 홈에 반영합니다. 조회 요청에는 요청 세대를, 잔액에는 로컬 revision을 확인해 오래된 응답이 최신 상태를 덮지 않도록 했습니다.

응답을 받지 못해 처리 여부를 알 수 없을 때는 같은 요청 ID로 재시도합니다. 서버가 기존 결과를 돌려줄 수 있게 하고, 티켓 차감과 사진 수집은 한 트랜잭션으로 처리합니다. 무료 재열람으로 시작한 요청도 끝까지 그 방식으로 유지해, 도중에 자정이나 충전 시각을 지났다는 이유로 새 티켓을 쓰지 않게 했습니다.

### 5. 교감이 끝난 뒤에야 시작되던 사진 로딩

강아지를 세 번 쓰다듬고 나면 사진을 기대하게 됩니다. 그런데 마지막 반응까지 끝난 뒤 서버 요청과 다운로드를 시작해서, 교감이 끝나고도 사진창에서 다시 기다려야 했습니다.

교감을 줄이는 대신 사진을 준비하는 시점을 앞당겼습니다. 사진 준비, 서버의 열람 권한 확정, 사진창 표시를 나누고 볼 권한에 따라 다르게 처리합니다.

| 사진 종류 | 준비 시점 |
| --- | --- |
| 내 사진·이미 모은 사진 | 간식을 먹고 쓰다듬기 단계에 들어서면 권한을 확인하고 다운로드·디코딩 |
| 처음 수집하는 사진 | 세 번째 입력이 인정되는 순간 공개 요청. 마지막 450ms 반응과 서버 처리·다운로드를 겹침 |

미리 준비하는 요청은 티켓이나 수집 기록을 바꾸지 않는 별도 API로 만들었습니다. 최종 사진 요청 때 서버가 권한을 다시 확인하고, 응답의 사진 ID가 준비본과 같을 때만 재사용합니다. 새 사진의 티켓 차감과 수집 기록은 함께 확정하며, 그 뒤 다운로드만 실패하면 다시 차감하지 않고 사진을 재시도합니다.

사진창은 기존처럼 마지막 반응이 끝나면 엽니다. 준비가 끝났으면 사진을 바로 보여 주고, 느린 연결에서는 로딩과 재시도를 남깁니다. 화질을 낮추거나 교감을 생략한 것은 아닙니다. 대신 내 사진·재열람에는 준비 요청이 한 번 추가되어, 호출 수 절감보다 체감 대기 시간을 줄이는 선택입니다.

## 직접 써 보며 바꾼 것

쓰다듬기는 한 번 길게 쓸면 끝나는 안도 고려했지만, 쓸기와 터치 모두 한 번에 하트 하나씩 채우도록 맞췄습니다. 손을 움직이기 어려우면 세 번 톡톡 눌러도 됩니다. 입력할 때마다 눈웃음과 꼬리 반응을 줘서, 하트 숫자를 보지 않아도 입력이 됐다는 것을 알 수 있게 했습니다. 동작 줄이기 설정에서는 눈웃음과 하트로 반응을 보여 줍니다.

강아지를 꾸미는 화면은 선택지가 늘수록 길어졌습니다. 귀와 기본 털색을 먼저 고르고, 더 고치고 싶은 사람만 세부 설정을 펼치게 했습니다. 아래로 스크롤해도 캐릭터 미리보기가 남아 있어 바뀐 모습을 계속 볼 수 있습니다.

등록한 사람은 검수 결과를 기다리는 동안에도 자기 강아지를 홈에서 확인하고 사진을 볼 수 있습니다. 다른 사람에게는 검수가 끝나기 전까지 실사 사진 주소를 보내지 않습니다.

검수 화면의 ‘유사 강아지’ 비교도 바꿨습니다. 흰 털이라는 이유로 비슷하다고 묶이는 것은 실제로 무엇을 고쳐야 하는지 판단하는 데 도움이 되지 않았습니다. 지금은 소품까지 모든 꾸밈 설정이 일치할 때만 ‘꾸밈 설정이 같은 강아지’로 표시합니다. 설정이 같다는 이유만으로 승인을 막거나 검수 메모를 요구하지 않고, 사진을 보고 판단할 때 참고하도록 했습니다.

같은 사진을 다시 보는 동선도 두었습니다. 홈에서는 강아지와 놀고 사진을 보지만, 앨범에서는 사진을 바로 엽니다. 모아 둔 사진을 찾을 때마다 간식을 주고 쓰다듬는 과정을 반복할 필요는 없다고 봤습니다.

## 테스트

사진창을 닫은 뒤 성공 응답이 오거나, 같은 보상 요청을 다시 보내는 상황을 Vitest와 Testing Library로 재현합니다. 앨범 이관은 PGlite에서 SQL을 실행해 확인합니다. 같은 사용자를 두 번 이관해도 사진이 추가로 지급되지 않는지, 구버전에서 남긴 기록이 빠지지 않는지를 검사합니다.

### 기존 계정을 지우지 않고 정상 동선부터

개발자 계정에는 이미 모은 사진이 많아 티켓이 줄지 않았고, 두 장을 소진한 뒤 광고로 이어지는 구간을 반복 확인하기 어려웠습니다. 운영 기록을 지우는 대신 테스트마다 별도의 사용자와 데이터를 만들어, 정상 앱 화면에서 같은 동선을 재현하도록 했습니다.

| 확인하려는 것 | 자동으로 재현한 범위 |
| --- | --- |
| 티켓 소진 뒤 광고 진입 | 무료 두 번 → 0장 → 광고 보상 → 간식·쓰다듬기 → 사진. 취소·오류·중복 보상·앱 복귀도 검사 |
| 사진 준비와 중간 이탈 | 내 사진·재열람 사전 준비, 세 번째 입력의 요청 시점, 느린 다운로드·재시도, 닫힌 사진창이 다시 열리지 않는지 검사 |
| 등록자와 다른 사용자 연결 | SQL에서 등록·검수·추가 사진 승인을 검사. 별도 A/B 브라우저에서는 승인된 강아지의 사진 수집·좋아요·재접속과 등록자 집계 0 → 1 → 0을 확인 |
| 충전 알림 | 예약 SQL부터 발송 처리·응답 판정까지 연결. 미동의·해제는 발송하지 않고, 결과가 불명확하면 자동 재전송하지 않는지 검사 |

Playwright는 360×640·390×844·430×844의 실제 앱 화면을 조작합니다. 다만 브라우저의 서버·토스 SDK 응답과 알림의 최종 전송은 테스트용으로 대체합니다. 실제 Edge 처리기와 SQL은 따로 검사하며, 운영 사진·사용자 기록을 바꾸거나 실제 광고·푸시를 보내지 않습니다.

### QA를 넓히며 발견한 문제

- **개발 모드 첫 진입:** StrictMode에서 첫 집 조회가 취소된 뒤 다시 시작되지 않았습니다. 취소된 요청은 재시작할 수 있게 하고, 늦은 응답이 새 결과를 덮지 않는 회귀 테스트를 추가했습니다.
- **사진 준비 API 연결:** SQL 테스트에서 새 요청이 기존 DB 허용 목록에 없어 거부되는 것을 확인했습니다. 기존 기록을 보존하는 후속 마이그레이션을 마련하고, preview의 준비 요청도 과거 사진 선물 이관을 실행하지 않도록 고쳤습니다.
- **간헐적으로 실패하던 검사:** 앨범 SQL 테스트가 앞선 검사에서 바꾼 사진 데이터를 무작위로 사용하고 있었습니다. 검사마다 독립된 데이터를 쓰도록 고친 뒤 관련 18개 검사를 별도 실행 5회 연속 통과했습니다. 서비스 규칙이 아니라 테스트 데이터 간섭을 고친 경우입니다.

발견한 문제는 한 번 고치고 끝내지 않고 다시 실행할 검사로 남겼습니다. 변경 영역의 단위 테스트·타입 검사 후 전체 회귀와 모바일 E2E를 실행하며, 실패를 재시도로 숨기지 않습니다.

<details>
<summary>최근 검증 기록 · 2026-09-12 로컬 작업본</summary>

- SQL/RPC 158개, 검수 HTTP·AIT 보관·설정 72개, 실제 Edge 처리기 2개(11단계) 통과
- Vitest 1,062개, 모바일 E2E 27개, 개발 StrictMode 첫 진입 1개 통과
- 앱·브라우저 타입 검사와 production 설정의 웹 빌드 통과

위 수치는 당시 로컬 작업본의 실행 기록입니다. 실제 업로드부터 운영자 승인까지를 두 기기에서 잇는 검증과 운영 DB의 동시 요청 검증은 별도로 남아 있습니다. 이 결과가 운영 서버 배포나 새 AIT 업로드·출시 완료를 뜻하지는 않습니다.

</details>

광고와 권한창처럼 토스 앱이 관여하는 동작은 자동 테스트만으로 확인할 수 없어 Android·iOS의 Toss QR에서 별도로 검증합니다. 외부 앱에서 공유 링크를 여는 동작도 실제 기기의 결과와 구분해서 기록합니다.

## 실행하기

Node.js 24와 npm을 사용합니다. 기본 preview는 서버 비밀값 없이 샘플 데이터로 실행됩니다.

```bash
git clone https://github.com/swaan-kim/cute-enough.git
cd cute-enough
npm ci
npm run dev
```

[첫 방문 화면](http://localhost:5173/?scenario=first-user)에서 공개 4마리의 홈을 확인할 수 있습니다.

| 명령 | 용도 |
| --- | --- |
| `npm test` / `npm run typecheck` | UI·로직 테스트 / 타입 검사 |
| `npm run test:review` / `npm run test:ait` | 검수·DB 테스트 / AIT 보관 규칙 테스트 |
| `npm run review` | `127.0.0.1:4178/review` 로컬 검수 도구 |
| `npm run build:web` | 샘플 웹 빌드 |
| `npm run build:private` / `npm run build:preview` | 테스트 AIT → `AIT/TEST` |
| `npm run build:production` | 운영 업로드 후보 → `AIT/LATEST` |
| `npm run ait:check` / `npm run deploy` | 후보 검증 / 검증된 파일 업로드 |

AIT는 공통 빌드 잠금과 입력 변경 검사를 거쳐 생성합니다. `AIT/LATEST/release.json`의 deploymentId·SHA-256을 실제 파일과 대조한 뒤 업로드하며, 업로드 과정에서 다시 빌드하지 않습니다.

README는 로컬 구현을 기준으로 작성했습니다. 운영 DB와 출시된 AIT에 반영된 범위는 다를 수 있습니다. 로컬 검수 도구 설정은 [검수 안내](docs/REVIEW_CONSOLE.md)를 참고해 주세요.
